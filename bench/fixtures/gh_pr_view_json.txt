Each process keeps its token in memory and asks `Session::is_expired` before a call. Because the comparison was strict, a token was still considered valid during the exact second it expired, and because refresh only happened after expiry, the first request of every hour went out with a dead token, got a 401, and was retried. The retry hid the bug from most dashboards; it only showed up as a steady one-per-hour 401 rate per process in the gateway logs, which is how #398 was found.\n\n## Changes\n\n- `auth/session.rs`: `Session::is_expired` now compares with `>=` instead of `>`, so a token whose `expires_at` equals `now` is treated as expired. This was the off-by-one reported in #398.\n- `auth/refresh.rs`: a token is refreshed when less than `REFRESH_MARGIN` (60 s) of its lifetime remains, not when it is already expired. The margin is a constant rather than a setting on purpose: nothing needs to tune it and a configurable margin of zero would bring the bug back.\n- `auth/clock.rs`: the clock used by sessions is injected, so tests no longer sleep. `SystemClock` is the default; `FixedClock` is test-only and lives behind `#[cfg(test)]`.\n- `billing/invoice.rs`: the invoice client reused the session token without checking it. It now goes through `Session::bearer()`, which refreshes on the way.\n- `CHANGELOG.md`: one entry under Fixed.\n\n## Why not refresh on every request\n\nRefreshing on each call doubles the load on the identity provider for no benefit; the provider rate-limits refreshes per client at 30/min, and the batch importer alone makes about 400 calls per minute at peak. Safe to deploy in any order relative to the identity provider.
